## 1. Продукт и наблюдаемый успех

Приложение показывает одну большую цель как схему: узлы-задачи, стрелки и якорь цели. У задачи есть ответственный и оценка. Оценка предыдущей задачи написана на исходящей стрелке. Двойной щелчок по задаче открывает её канбан из четырёх колонок. Доля карточек в «Готово» видна на узле.

Успех демо выполнен, когда на одной цели одновременно видно всё перечисленное:

1. Основатель собрал схему из нескольких задач и стрелок, сходящихся к якорю.
2. На узле-задаче написаны ответственный и оценка.
3. На каждой исходящей стрелке та же оценка, что у её источника.
4. После переноса карточки в «Готово» узел показывает процент `round(100 * doneCount / totalCount)`.
5. Даты и состав критического пути от этого переноса не меняются.

Пример цели для ручного прогона — «Постройка дома для продажи». Числовой эталон алгоритма — раздел 13, не этот заголовок.

## 3. Кто пользуется

Одна компания `demo-company`. Учётки, если таблица пользователей пуста:

| Email | Пароль | Имя |
|---|---|---|
| founder@demo.local | demo123 | Основатель |
| worker1@demo.local | demo123 | Иван Петров |
| worker2@demo.local | demo123 | Мария Сидорова |

Любой пользователь этой компании читает и меняет любую цель компании. Роль в JWT не проверять. `companyId` брать только из токена. Чужой `companyId` в теле игнорировать, если поле вообще прислали: запрос с ним не расширяет доступ.

Лимита числа людей на цель в интерфейсе нет. Нагрузку на сотни пользователей не обещать и не проверять.

Вход: `POST /api/v1/auth/login` `{ email, password }` → JWT. Пароль в ответах не возвращать. `GET /api/v1/auth/me` — текущий пользователь. `GET /api/v1/users` — id, name, email пользователей своей компании, для списков ответственных.

## 4. Термины

| Термин | Единственное значение |
|---|---|
| Цель | Запись `goals` и её якорь на схеме |
| Задача | Узел `type = task`. У него одна доска |
| Якорь | Единственный узел `type = goal_anchor`. Доски нет |
| Стрелка | Ребро A → B. Вес и подпись всегда равны оценке A |
| Путь | Любая цепочка стрелок до якоря. Отдельного объекта нет |
| Оценка | Число `estimateValue` + единица `hour \| day \| week` на узле-источнике |
| Карточка | Работа внутри доски задачи. На стрелку и на критический путь не влияет |

Узел задачи и карточка — разные вещи. Ответственный узла (`assigneeId`, один) и ответственные карточки (список) тоже разные. Оценка узла и учёт минут на карточке друг в друга не пересчитываются.

## 5. Время

### 5.1. Единицы

```
toDays(value, unit) =
  hour → value / 8
  day  → value
  week → value * 7
```

Иная единица — ошибка `400` `BAD_ESTIMATE`. `value` — число ≥ 0. День в этой формуле — календарный. Выходные не вычитаются. Час не бывает отдельными сутками, пока не накопит 1/8 дня.

### 5.2. Одно число

Оценка хранится только на узле. При каждом сохранении графа сервер переписывает каждое ребро:

```
edge.durationValue = source.estimateValue
edge.durationUnit  = source.estimateUnit
edge.label         = format(source.estimateValue, source.estimateUnit)
```

`format`: единица `hour` → `ч`, `day` → `д`, `week` → `нед`. Пример: `5` и `day` → `5д`. Значения длительности ребра в теле PUT сервер не использует. У якоря оценка всегда 0, исходящая подпись `0д`.

Новая задача, если оценку не передали: `1` и `day`. И на сервере, и в кнопке «+ Задача» — одно и то же значение 1 день.

### 5.3. Шкала и drag

У цели есть `scaleStart` (`YYYY-MM-DD`). Если при создании не передали: взять `deadline`, если он есть, иначе календарную дату `createdAt` в UTC.

Ось X: 48 пикселей = 1 календарный день. `x = 0` — это `scaleStart`. Клиент ставит `x` кратным 48. Сервер всё равно считает:

```
dayIndex     = round(x / 48)
plannedStart = addCalendarDays(scaleStart, dayIndex)
offset       = toDays(estimateValue, estimateUnit)
plannedEnd   = plannedStart, если offset = 0
             = addCalendarDays(plannedStart, ceil(offset)) иначе
```

`addCalendarDays` считает по UTC-календарю, без часового пояса браузера. Пример: `plannedStart = 2026-09-01`, оценка 3 дня → `plannedEnd = 2026-09-04`. Оценка 4 часа = 0,5 дня → `ceil(0.5) = 1` → `plannedEnd = 2026-09-02`.

Даты в PUT сервер не принимает как источник истины. Их нет в теле либо они игнорируются: после записи клиент показывает даты из ответа.

Drag меняет `x` только этого узла. `y` на даты не влияет. Другие узлы, их оценки и стрелки не сдвигаются. Смена `scaleStart` не меняет `x`: все даты пересчитываются от новой точки отсчёта.

Сравнение с дедлайном использует точный `offset`, не `ceil`. См. раздел 6.

## 6. Критический путь

Считать по оценкам узлов, не по положению на шкале и не по входящей стрелке.

Вес ребра A → B равен `toDays` оценки A. Якорь добавляет 0. Узел, из которого якорь недостижим, в расчёт не входит, каким бы большим ни было его число.

Длина маршрута до якоря — сумма `toDays` оценок всех задач на маршруте, без якоря. Критическая длина — максимум среди таких маршрутов. Если задач, из которых якорь достижим, нет, критическая длина 0.

Подсветить все узлы-задачи и все рёбра, которые лежат хотя бы на одном маршруте с этой максимальной длиной. При равных суммах подсвечивать все такие маршруты, а не первый id в массиве. Якорь стилем критического пути не красить. При длине 0 не красить ничего.

`deadlineExceeded` истинен только когда одновременно:

- у цели задан `deadline`;
- критическая длина > 0;
- у каждой подсвеченной задачи есть `plannedStart`.

Иначе ложь. Дата финиша:

```
start = минимум plannedStart среди подсвеченных задач
finishInstant = UTC-полночь(start) + criticalLengthDays * 86400000 мс
finishDate = календарная дата finishInstant в UTC
deadlineExceeded = finishDate > deadline
```

Равенство дедлайну — не превышение. Перенос карточки это значение не меняет: в формулу входят только оценки и `plannedStart`.

Ответ `GET` графа всегда содержит уже посчитанные `criticalNodeIds`, `criticalEdgeIds` и `deadlineExceeded`. Отдельная ручка критического пути не нужна.

## 7. Статус узла и прогресс

Поля `status` и `progress` считает только сервер.

`totalCount` — число карточек доски. Архива нет. `doneCount` — сколько из них в колонке `done`.

Если `totalCount = 0`:

- статус ручной: `not_started`, `in_progress` или `done`;
- у новой задачи — `not_started`;
- процента нет (`progress = null`).

Если `totalCount ≥ 1`:

- ручной статус погашен и больше не хранится;
- `progress = round(100 * doneCount / totalCount)` — целое 0…100;
- все карточки в `todo` → `not_started`;
- все карточки в `done` → `done`;
- иначе → `in_progress` (колонки `in_progress` и `testing` сами по себе отдельного статуса узла не дают).

Пересчёт в той же транзакции, которая создала, передвинула или удалила карточку. `PUT` графа статус и прогресс не записывает.

Пока карточек нет, ручной статус меняется только так:

`PATCH /api/v1/visual-paths/goals/:goalId/nodes/:nodeId/manual-status`  
`{ "status": "not_started" | "in_progress" | "done" }`

Если карточки уже есть — `409` `STATUS_DERIVED`, статус в базе не менять. Якорю ручной статус не задаётся.

На схеме: при `progress = null` текст «Не начата» / «В работе» / «Готово»; иначе текст `N%`. Цвет узла: не начата — нейтральный, в работе — синий, готово — зелёный. Критический путь — дополнительная обводка, она не заменяет цвет статуса.

Статус цели (`draft | active | completed | archived`) от узлов и карточек не зависит. Сам он меняется только через `PATCH` цели. В список попадают цели с `archivedAt = null`.

## 8. Граф и жизнь доски

У цели ровно один якорь. `POST` цели создаёт его в той же транзакции: заголовок «Цель», `type = goal_anchor`, оценка 0, `x = 720`, `y = 200`. Удалить якорь нельзя. Второй якорь в `PUT` — `400` `ANCHOR_COUNT`. Тело без этого якоря — `400` `ANCHOR_REQUIRED`. Доски у якоря нет. `GET` доски якоря — `400` `NOT_A_TASK`. Двойной щелчок по якорю открывает свойства цели, не канбан.

`PUT /api/v1/visual-paths/goals/:goalId/graph` заменяет набор узлов и рёбер по правилам ниже, а не «удалить все строки и вставить заново», если это снимает доски.

Сопоставление узла — по `id`.

| Ситуация | Что сделать |
|---|---|
| Тот же `id`, тип остался `task` | Обновить координаты, заголовок, описание, ответственного, оценку. Доску и карточки не трогать |
| Новый `id` | Создать `task` и пустую доску |
| `id` задачи нет в теле | Удалить задачу, её рёбра, доску, карточки, пункты чек-листа, комментарии, интервалы времени, таймеры и историю |
| В теле просят сменить тип | `400` `NODE_TYPE_IMMUTABLE` |

Рёбра, которых нет в теле, удалить. Новое ребро создать. Ребро на отсутствующий id — `400` `EDGE_NODE_MISSING`. Петля и вторая стрелка в ту же пару source→target — `400` `EDGE_DUPLICATE`. Цикл — `400` `GRAPH_CYCLE_DETECTED`, база без изменений.

Версии:

- в теле `version` не равен `goals.graphVersion` → `409` `GRAPH_VERSION_CONFLICT`, база без изменений;
- равен и нормализованное тело отличается → записать, затем `graphVersion += 1`;
- клиент после `409` заново читает граф и не сливает изменения сам.

Нормализация для сравнения: узлы по `id`, рёбра по `id`, даты и подписи не входят в сравнение клиента — их выставляет сервер. Повторная отправка того же документа с уже увеличенной версией — обычный успешный `PUT`, если клиент прислал версию из последнего ответа. Отдельной идемпотентности «тот же version обязан вернуть успех» нет: несовпадение версии всегда `409`.

`assigneeId` либо `null`, либо id пользователя той же компании. Иначе `400` `ASSIGNEE_NOT_IN_COMPANY`.

## 9. Модель данных

Даты — тип `date`, формат `YYYY-MM-DD`. Времена событий — `timestamptz`.

**goals:** `id`, `companyId`, `title`, `description`, `deadline` (date, null), `scaleStart` (date, not null), `status`, `graphVersion` (int, старт 1), `createdBy`, `createdAt`, `updatedAt`, `archivedAt`.

**graph_nodes:** `id` (uuid, приходит с клиента для задач; якорь может создать сервер), `goalId`, `type` (`task` \| `goal_anchor`), `title`, `description`, `x`, `y`, `plannedStart`, `plannedEnd`, `status`, `progress` (int, null), `assigneeId` (null), `estimateValue`, `estimateUnit`. Полей `pathId`, `milestone`, `progressCached` в контракте нет. Если `progress_cached` уже есть в таблице — хранить туда то же число, что и `progress`, либо перестать его писать; читать клиент должен `progress` из JSON.

**graph_edges:** `id`, `goalId`, `sourceNodeId`, `targetNodeId`, `durationValue`, `durationUnit`, `label`. Все три последних поля серверные.

**boards:** `id`, `nodeId` уникален, только для `task`.

**cards:** `id`, `boardId`, `columnKey` (`todo` \| `in_progress` \| `testing` \| `done`), `position` (int, с нуля, без дыр внутри колонки), `title`, `description`, `priority` (`low` \| `medium` \| `high` \| `critical`), `dueDate` (date, null), `archived` нет.

**card_assignees:** `cardId`, `userId`. Пара уникальна.

**checklist_items:** `id`, `cardId`, `text`, `done`, `position`.

**comments:** `id`, `cardId`, `authorId`, `text`, `createdAt`, `updatedAt`.

**time_entries:** `id`, `cardId`, `userId`, `minutes` (int ≥ 1), `note`, `createdAt`.

**timers:** `id`, `cardId`, `userId`, `startedAt`. Не больше одного живого таймера на пару карточка+пользователь.

**card_events:** `id`, `cardId`, `actorId`, `type`, `payload` (json), `createdAt`. Записи не править и не удалять.

Типы событий: `created`, `updated`, `moved`, `comment_added`, `comment_updated`, `comment_deleted`, `checklist_set`, `time_logged`, `timer_started`, `timer_stopped`, `deleted`.

### 10.1. Цели

### 10.3. Доска и карточки

`GET /api/v1/visual-paths/nodes/:nodeId/board` — `{ nodeId, title, columns: [{ key, title, cards }] }`. Колонки строго:

| key | Заголовок | position |
|---|---|---|
| todo | Задача | 1 |
| in_progress | В работе | 2 |
| testing | Тестирование | 3 |
| done | Готово | 4 |

Карточки внутри колонки по `position` по возрастанию. В карточке списка уже есть title, priority, dueDate, assigneeIds, done пунктов чек-листа `doneItems/itemCount`, сумма минут.

`POST /api/v1/visual-paths/nodes/:nodeId/cards` `{ "title": "…" }` — карточка в конец `todo`. Пустой title — `400`.

`GET /api/v1/visual-paths/cards/:cardId` — карточка целиком: описание, assigneeIds, checklist, comments, timeEntries, runningTimer текущего пользователя (`null` или `{ startedAt }`), сумма минут.

`PATCH /api/v1/visual-paths/cards/:cardId` — любое подмножество: `title`, `description`, `priority`, `dueDate`, `assigneeIds`. `assigneeIds` заменяет список. Один `updated` в историю с именами изменившихся полей.

`POST /api/v1/visual-paths/cards/:cardId/move` `{ "columnKey": "testing", "position": 0 }`. Вынуть карточку и вставить так, чтобы в целевой колонке она стала индексом `position` (0 — верх). Обе колонки заново пронумеровать с нуля. Событие `moved`.

`DELETE /api/v1/visual-paths/cards/:cardId` — удалить карточку и её дочерние строки, событие `deleted` записать до удаления или хранить `cardId` в событии так, чтобы история узла ещё читалась: события не каскадно уничтожать. После удаления перенумеровать колонку и пересчитать статус узла.

`PUT /api/v1/visual-paths/cards/:cardId/checklist` `{ "items": [{ "id": "optional", "text": "…", "done": false }] }` заменяет список. Порядок массива = `position`. Событие `checklist_set`.

`POST /api/v1/visual-paths/cards/:cardId/comments` `{ "text": "…" }`  
`PATCH` и `DELETE /api/v1/visual-paths/cards/:cardId/comments/:commentId` — только автор.

`POST /api/v1/visual-paths/cards/:cardId/time-entries` `{ "minutes": 30, "note": "" }` — минуты целое ≥ 1.

`POST .../timer/start` — если у этого пользователя на этой карточке уже есть таймер, `409` `TIMER_ALREADY_RUNNING`.  
`POST .../timer/stop` — минут = `max(1, round(elapsedMs / 60000))`, таймер удалить, появилась запись `time_entries`. Нет таймера — `404` `TIMER_NOT_FOUND`.

`GET /api/v1/visual-paths/cards/:cardId/history` — события по времени, новые ниже или выше, но стабильно: по `createdAt` по возрастанию. В каждом событии есть имя автора.

## 11. Экраны

Три рабочих экрана плюс вход. Отдельный визуальный язык не проектировать: опереться на уже лежащие стили, подписи по-русски, состояние на экране видно без догадки.

1. **Вход.** Почта и пароль. Ошибка входа показывает `message`.
2. **Список целей.** Название, дедлайн, кнопка создания. Пустой список — кнопка «Создать цель».
3. **Схема.** Холст, создание задачи, выбор узла, панель свойств, сохранение.
4. **Канбан задачи.** Четыре колонки, карточка, возврат на схему с тем же узлом в виду.

Схема, обязательно:

- перетаскивание узла, пан, зум;
- стрелка от правого порта к левому;
- цикл не рисуется, на экране текст «Нельзя создать цикл в зависимостях»;
- двойной щелчок по задаче открывает её канбан;
- удаление задачи спрашивает подтверждение и не предлагает удалить якорь;
- панель задачи: название, ответственный (список учёток и пункт «не назначен»), оценка (число и часы/дни/недели), кнопка удаления;
- под узлом видны имя ответственного или «без ответственного», оценка (у якоря оценку не показывать), процент или текст статуса;
- подпись стрелки совпадает с оценкой источника сразу после её правки, не только после перезагрузки;
- критические задачи и стрелки отличимы от остальных;
- если `deadlineExceeded`, над холстом есть фраза, что расчётная дата финиша позже дедлайна, и сама дата финиша из раздела 6;
- сохранение само, с задержкой около 1 с, и вручную. На экране есть состояние «есть изменения» / «сохранение…» / «сохранено» / текст ошибки;
- конфликт версии заменяет холст ответом сервера после повторного `GET` и показывает `message`.

Панель не редактирует «длительность ребра» отдельно от оценки узла. Отдельного поля даты на узле нет: дата следует из X и видна текстом `plannedStart–plannedEnd`.

Свойства цели (с якоря): название, описание, `scaleStart`, дедлайн.

## 12. Канбан

Колонки не переименовываются и не добавляются. Карточка перетаскивается между колонками и внутри колонки.

На карточке в демо есть только: название, описание, ответственные, срок, приоритет, чек-лист (текст и галочка), комментарии, учёт времени (ручные минуты и один таймер), история. Описание — обычный текст, без HTML.

Создание — кнопка в колонке и ввод названия. Клик по карточке открывает её полностью поверх доски. Закрытие возвращает на доску, не на схему. На доске есть ссылка «К схеме».

Приоритет по умолчанию `medium`. Срок пустой, пока его не поставили. Чек-лист без людей и без собственных сроков.

История пишется на действия из раздела 10.3. Открытие карточки историю не пишет.

## 13. Числовой эталон

Этот граф — фикстура теста, не обязательный сид в интерфейсе. Сид пользователей делать. Готовую схему дома в базу при старте не класть: её собирает человек в приёмке.

`scaleStart = 2026-08-01`, `deadline = 2026-11-01`. Оценки в днях.

| id | Узел | Оценка | Куда |
|---|---|---|---|
| db | Схема БД | 3 | api |
| api | API заказов | 5 | pay |
| pay | Платежи | 4 | qa |
| ui | Дизайн витрины | 2 | cat |
| cat | Каталог | 4 | cart |
| cart | Корзина | 3 | qa |
| qa | Интеграционный прогон | 0 | goal |
| goal | Цель | 0 | — |
| lone | Закупка рекламы | 100 | никуда |

Ожидание:

- критическая длина = 12;
- `criticalNodeIds` = db, api, pay, qa;
- ui, cat, cart, lone, goal в критический набор не входят;
- `lone` с оценкой 100 путь не перебивает;
- подписи рёбер: `3д`, `5д`, `4д`, `2д`, `4д`, `3д`, `0д`;
- входящая стрелка не становится оценкой цели: у «Платежи» остаётся 4, а не 5.

Даты при `x = 0` у всех: `plannedStart = 2026-08-01`. У «Платежи» `plannedEnd = 2026-08-05`. Финиш критического пути = 2026-08-01 + 12 дней = 2026-08-13. Дедлайн 2026-11-01 не превышен.

Тот же граф, но у db, api, pay и qa `plannedStart = 2026-10-25` (остальные узлы могут оставаться на 2026-08-01). Финиш = 2026-11-06. `deadlineExceeded = true`. Состав пути прежний: сдвиг по X маршрут не меняет.

Второй граф для равенства: две цепочки по 5 дней в один якорь и ничего больше. Подсвечены обе цепочки целиком.

Половина дня: оценка 4 часа, `x = 0`, `scaleStart = 2026-09-01` → `plannedEnd = 2026-09-02`, вклад в критическую длину = 0,5.

Статус на любой схеме из этого раздела при нуле карточек остаётся ручным и путь не меняет. Одна карточка в `done` даёт прогресс 100 и статус `done`, `criticalNodeIds` те же.

## 14. Приёмка демо

Проверяет человек. Всё ниже должно получиться без догадки.

1. Войти как `founder@demo.local` / `demo123`. Создать цель «Постройка дома для продажи», дедлайн `2026-11-01`, начало шкалы `2026-08-01`. На холсте сразу один якорь «Цель».
2. Добавить задачи «Фундамент» (10 дней, ответственный Иван Петров) и «Проект» (5 дней, Мария Сидорова). Провести стрелки в якорь. На стрелках `10д` и `5д`. Под узлами видны имена и оценки.
3. Выйти. Войти как `worker1@demo.local`. Открыть ту же цель и сменить оценку «Фундамент» на 12 дней. Ошибка доступа не появляется. Исходящая стрелка становится `12д`.
4. Двойной щелчок по «Фундамент» открывает колонки «Задача», «В работе», «Тестирование», «Готово».
5. Создать карточку, заполнить описание, ответственного, срок, приоритет, пункт чек-листа, комментарий, ручные минуты. Провести карточку по всем четырём колонкам. В «Готово» на схеме у узла 100%. Вернуться как основатель: даты узлов и подсветка критического пути те же, что до карточки.
6. Вторая карточка в «Задача» при первой в «Готово» даёт 50% и статус «В работе».
7. Удалить обе карточки. Процент исчезает, узел снова «Не начата», пока ручной статус не поменяют.
8. Соединить узел сам с собой или замкнуть цепочку нельзя.
9. Перетащить «Фундамент» вправо по сетке дня. Меняются его `plannedStart` и `plannedEnd`. «Проект» и якорь остаются на своих датах. Оценка не меняется.
10. Построить эталон раздела 13 (через интерфейс или фикстуру теста) и сверить 12 дней, набор узлов и оба исхода дедлайна.
11. Сохранить граф, не убирая «Фундамент», добавить на него карточку, подвинуть узел, сохранить снова. Карточка на месте.
12. Сохранить граф без «Фундамент». Карточек этой задачи больше нет, открыть её канбан нельзя.

Пункты про token Host, viewer, метки, WIP, файлы, английский и portal в эту приёмку не входят.

## 15. Тесты, без которых сдача не считается

Автоматические:

1. `toDays` и оба графа раздела 13, включая узел 100 дней вне маршрута и две равные цепочки.
2. `plannedEnd` для 3 дней и для 4 часов из раздела 5.3.
3. `PUT` с тем же id задачи не удаляет карточку; `PUT` без id удаляет карточку.
4. `PUT` с полем статуса в узле не затирает статус, выведенный из карточек. Если поле вообще отвергается валидацией — клиент его не шлёт, а отдельный тест ручного `PATCH` при живых карточках ждёт `STATUS_DERIVED`.
5. Цикл → `GRAPH_CYCLE_DETECTED`. Чужая версия → `409`, данные прежние.
6. Второй пользователь компании сохраняет граф цели первого.
7. В `PUT` нельзя убрать якорь и нельзя добавить второй.

Ручной прогон — раздел 14. Для пунктов 1–9 и 11–12 достаточно интерфейса. Пункт 10 можно закрыть автотестом раздела 13, если в отчёте есть фактические `criticalNodeIds` и обе даты финиша.
