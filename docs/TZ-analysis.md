## 1. Резюме

ТЗ проработано **хорошо**: есть стратегия Standalone First, глоссарий, API-контракт, модель данных, критерии приёмки. Главный риск — **scope канбана «как Кайтен»** при одновременной разработке **timeline-canvas «как draw.io-lite»**. Для пары «разработчик + AI» реалистичный standalone MVP — **10–14 недель** календарно при полном scope v1; **6–8 недель** — при согласованном урезании (см. §4).

## 3. Противоречия и неясности в текущем ТЗ

1. **§0.5 vs §5.3:** в MVP заявлено «CRUD+DnD+описание/assignees», но §5.3 и UAT требуют чек-листы, комментарии, WIP, блокировки, историю, шаблоны, учёт времени — это уже **full kanban**, не MVP.
2. **§15 UAT п.10** (token refresh через Host) относится к **виджету**, не к standalone — для Phase 5 не применимо; вынести в UAT Phase 6.
3. **§6.1 vs §6.2:** длительность на ребре и `plannedStart`/`plannedEnd` узла — формулы пересчёта **не зафиксированы** (что первично при drag: дата или estimate?).
4. **FR-C-12 Undo/Redo:** «локально в сессии» + «сервер хранит актуальную версию» — не описано, **когда** пушить на сервер (debounce? по Ctrl+S?).
5. **Assignees в standalone:** нет API списка пользователей компании — нужен mock или минимальный `GET /users`.
6. **Прогресс узла (§6.3):** при смешении ручного статуса и авто по карточкам — приоритет не определён.

## 4. Предложения: упростить / улучшить

### 4.1. Упростить (рекомендуем для MVP)

| Область | Сейчас в ТЗ | Предложение MVP | Экономия |
|---------|-------------|-----------------|----------|
| Канбан | «Полный Кайтен» | CRUD, D&D, описание, assignees, метки, приоритет, due, чек-лист, комментарии | ~2–3 нед |
| Канбан v1.1 | — | WIP, block, history, templates, таймер, архив, массовые действия | — |
| Auth standalone | OTP как portal | Email+password JWT (OTP — перед widget) | ~3–5 дн |
| Graph API | PUT whole + PATCH granular | MVP: PUT whole graph + debounced autosave; PATCH — v1.1 | ~1 нед |
| Canvas | lanes + minimap + auto-layout | React Flow + timeline overlay; minimap/auto-layout — v1.1 | ~1–2 нед |
| Export | PNG, SVG, JSON | JSON backup v1; PNG — v1.1 | ~3–5 дн |
| Notifications | Events + polling | Badge «есть непрочитанное» без полноценной ленты | ~1 нед |
| Undo/Redo | 50 шагов | 20 шагов, только canvas (не канбан) | ~3 дн |
| i18n | ru + en | ru-only MVP, ключи через i18next сразу | ~3–5 дн |
| RBAC | 4 роли на goal | owner / member / viewer (editor = member с флагом) | ~2–3 дн |

### 4.2. Улучшить (добавить в ТЗ)

| Улучшение | Описание |
|-----------|----------|
| **Явная формула timeline** | Документ: `plannedEnd = plannedStart + node.estimate`; ребро добавляет lag; критический путь = longest path sum. |
| **Autosave contract** | Debounce 1–2 с, индикатор «сохранено / конфликт», hotkey Ctrl+S. |
| **Seed/demo data** | Одна цель «Два пути к MVP» (Приложение A) из коробки — ускоряет демо. |
| **Feature flags** | `VITE_FEATURE_*` для поэтапного включения канбан-фич без веток. |
| **OpenAPI first** | Сгенерировать типы клиента из swagger — меньше рассинхрона FE/BE. |
| **E2E smoke** | 3 сценария: создать цель → нарисовать граф → провести карточку Done. |
| **ADR-001 Canvas** | Зафиксировать выбор **@xyflow/react** (ex React Flow) — уже в экосистеме React, DAG, 200+ nodes. |
| **Метрики demo** | На цели: % done узлов + дней до дедлайна по критическому пути — «вау» для заказчика. |

### 4.3. Не упрощать (ядро продукта)

- DAG + запрет циклов (UI + API)
- Timeline по оси X с привязкой дат
- 4 фиксированные колонки канбана
- Связь прогресса узла ↔ Done-карточки
- `companyId` / tenant isolation
- `graph_version` + 409 при конфликте
- Standalone → widget через `AuthProvider` + `/api/v1/visual-paths`

## 5. Оценка трудозатрат (1 разработчик + AI)

## 6. Рекомендуемый порядок согласования с заказчиком

1. Подписать **вариант scope**: A (MVP) или B (full v1).
2. Закрыть блок **§2.3 (схема/время)** — без этого нельзя кодить critical path.
3. Закрыть **assignees/users** в standalone.
4. Зафиксировать **дату демо** и критерии go/no-go на Phase 6.
5. Обновить ТЗ → v1.2 с таблицей «MVP / v1.1 / out of scope».
